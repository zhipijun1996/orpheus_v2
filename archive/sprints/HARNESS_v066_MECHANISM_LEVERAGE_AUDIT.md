# Harness v0.6.6 — Mechanism Leverage Audit

## OBSERVE
A Route Engine can become locally coherent while accumulating opaque one-off mechanisms and terminology. A naive response such as “fewer mechanisms” would also suppress strong generative concepts.

## LOCALIZE
- `PROJECT_DATA`: project-specific mechanism discipline and reveal setup expectations belong in the existing Story Contract.
- `MODULE`: Pipeline/Gates should distinguish generative mechanisms from explanatory scaffolding.
- execution adapters: Forge/Review/Synthesis should apply the same distinction.
- `CORE`: unchanged.

## PATCH
- protect mechanism novelty during EXPLORE;
- classify mechanism-heavy work as `ENGINE / SUPPORT / PATCH` during BUILD/REVIEW;
- judge ENGINE ideas by narrative leverage, not novelty/count;
- treat deep PATCH dependency as complexity debt;
- allow late naming/explanation when decisive properties have prior observable setup;
- prefer plain-language mechanism statements without banning specialized terms that earn repeated use.

## CALIBRATE
Motivating and control cases are stored in `archive/calibration/CAL_MECHANISM_LEVERAGE.yaml` and remain outside ordinary creative context.

## REGRESS
1. High-leverage personality-overwrite-style ENGINE: survives and is explicitly protected from mechanism-count penalties.
2. ENGINE with necessary understandable SUPPORT rules and fair setup: remains viable.
3. Multi-level patch chain whose rules mainly repair previous rules: is classified as PATCH debt and routed toward simplification/rollback.
4. Reveal that names a mechanism late after earlier observable traces: remains fair.

## DISTILL
No hard mechanism-count limit was introduced. No new Core rule or standalone active Harness module was added. The existing Pipeline and Gates were refined; project-specific detail stays in the already-loaded Story Contract.
